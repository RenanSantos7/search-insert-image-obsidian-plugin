# 06 — Internationalization (i18n)

**Plan sections:** "Internationalization (`src/i18n/`)".

## Goal

Provide zero-dependency internationalization support that automatically adapts to the user's interface language configured in Obsidian, with English as the fallback and base locale, and Brazilian Portuguese as the supported locale.

## Checklist

- [x] Create `src/i18n/locales/en.ts` with all user-facing strings in English (single source of truth for string keys).
- [x] Create `src/i18n/locales/pt-br.ts` implementing `Partial<typeof en>` with Brazilian Portuguese translations.
- [x] Create `src/i18n/locales/es.ts` implementing `Partial<typeof en>` with Latin American Spanish translations.
- [x] Implement `src/i18n/index.ts` with `t()` helper and Obsidian locale resolution (`getLanguage()`).
- [x] Refactor `src/commands.ts` to use `t()`.
- [x] Refactor `src/main.ts` (ribbon icon tooltip, notice, context menu) to use `t()`.
- [x] Refactor `src/modal.ts` (inputs, buttons, pagination, notices, error messages) to use `t()`.
- [x] Refactor `src/settings.ts` (tab headers, setting names, descriptions, provider labels) to use `t()`.
- [x] Refactor `src/insert.ts` (download errors, format warnings, notices) to use `t()`.
- [x] Refactor `src/providers/duckduckgo.ts` and `src/providers/google.ts` (error notices handled via modal with `t()`).
- [x] Verify build, lint, and vault install (`pnpm build`, `pnpm lint`, `node ./install.mjs`).

## Acceptance criteria

- All UI strings, notices, and settings adapt to the language configured in Obsidian (`en` vs `pt-BR`).
- No hardcoded user-facing strings remain in UI components.
- Zero extra runtime dependencies added to bundle.
- TypeScript compiler enforces type safety on translation keys.
